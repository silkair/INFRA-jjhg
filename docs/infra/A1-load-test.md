# A1 — 실제 API 트래픽으로 한계 측정

M2·M4의 확인은 health·내 정보·업로드 몇 건과 curl 반복뿐이었다. 실제 API 시나리오로 부하를 주고, 어디까지 버티는지와 무엇이 먼저 막히는지 측정했다.

## 방법

| 항목 | 값 |
|---|---|
| 도구 | k6 (노트북에서 실행. VM 3대와 같은 기기 — 측정 조건으로 명시) |
| 가상 사용자 | DB에 100명 시드(`scripts/seed-load-users.sh`). 토큰은 k6가 앱과 같은 규칙(HS512, subject = user id)으로 생성 |
| 시나리오 1회 | 내 정보 → 계약 목록 → (5회 중 1회) 계약 생성 + 상세 → 안 읽은 알림 수 ≈ 요청 4~5건 |
| 프로필 | smoke(1회) / steady(일정 속도 유지) / ramp(2분마다 5→10→20→40→60회/초) |
| 클러스터 | worker 2대(2 vCPU · 6GB), 앱 파드 1개(메모리 제한 768Mi), MySQL 1개, 커넥션 풀 기본값 10 |

## 1. 한계 측정 (ramp, 2026-11-23)

| 구간 | 시나리오 (회/초) | 요청 (건/초) | p95 | 실패 |
|---|---|---|---|---|
| 0~6분 | 2 → 19 | 7 → 65 | 30~55ms | 0 |
| 6분~6분 50초 | 19 → 26 | 65 → 87 | 50~140ms | 0 |
| 6분 50초~7분 | 27~28 | 91~95 | 230~260ms | 0 |
| 7분 10초~ | 목표 30~60 | **95~105에서 정체** | 0.7초 → 7~8초 | 0 |

- 처리 한계: **초당 약 100요청**. 그 이상은 처리량이 늘지 않고 대기만 쌓였다(포화)
- p95 100ms 이하를 지킨 구간: 초당 약 85요청까지
- 35,789건 중 실패 0건, 처리하지 못한 시나리오 3,124회(k6 가상 사용자 400명 소진)
- 근거: `evidence/A1-ramp-report.html` (k6 보고서, 10초 단위 그래프)

## 2. 병목 진단 (steady RATE=30, 4분, 조건 하나씩 변경)

| | 0. 처음 | 1. SQL 출력 끔 | 2. 앱을 다른 노드로 |
|---|---|---|---|
| 배치 | 앱·MySQL 모두 w1 | 모두 w1 | 앱 w2 / MySQL w1 |
| 처리량 (요청/초) | 92.7 | **97.9** | 83.1 |
| 응답 시간 중앙값 | 737ms | **314ms** | 1,030ms |
| p95 | 2.0초 | **1.65초** | 2.49초 |
| 처리 못 한 시나리오 | 598 | 278 | 1,271 |
| 커넥션 사용 중 / 대기 (2~3분 시점) | 10/10 · 84 | 10/10 · 8 | 10/10 · 79 |
| 커넥션 대기 시간 (평균) | 0.44초 | 0.24초 | 0.44초 |
| 커넥션 점유 시간 (평균) | 51ms | **35ms** | 51ms |
| 앱 CPU / MySQL CPU (코어) | 0.62 / 0.44 | 0.96 / 0.57 | 1.12~1.35 / 0.70 |
| 노드 CPU | w1 99% | w1 94% | w1 77%, w2 수집 지연(포화 추정) |
| 요청 1건당 커넥션 획득 | — | 2.0회 | 2.0회 |

**0 → 1. 직접 병목은 DB 커넥션 풀 고갈.** 모든 API의 p95가 약 2초로 같았다. 특정 쿼리가 아니라 커넥션 대기라는 공통 지점에서 막혔다는 뜻이다. 원인 하나는 개발용 SQL 출력(`show-sql`, `format_sql`)이 배포 환경(dev 프로필)에 켜져 있던 것. SQL을 쿼리 실행 중에 표준 출력으로 찍어서 커넥션 점유 시간이 늘었다. 끄자 점유 시간 31% 감소, 응답 중앙값 57% 감소.

**배치 원인.** 앱 CPU 요청값 200m(실사용 0.6~1코어), MySQL 100m(실사용 0.4~0.7코어). 스케줄러는 요청값으로 배치를 정하므로 둘을 같은 2코어 노드에 두었다. 요청값을 500m씩으로 현실화했다.

**1 → 2. 노드를 나누자 오히려 나빠졌다(예측 실패).** 앱→DB가 노드 간 네트워크를 거치게 되어 점유 시간이 다시 51ms. 옮겨 간 w2에는 Prometheus·Envoy·Redis·RustFS가 있어 포화됐다. 이때 w2의 MetalLB speaker가 liveness 검사 시간 초과로 재시작됐다(아래).

**결론.** 이 환경의 천장은 **앱 파드 하나가 쓸 수 있는 CPU**다(초당 약 90요청에 1코어 이상). 다음 개선은 파드를 늘려 두 노드의 CPU를 함께 쓰는 것(B1). 이를 막는 것은 앱 안의 스케줄러 중복 실행이다.

## 3. CPU 포화가 인프라 구성 요소로 번진 사례

2단계 측정 중(07:16 UTC) w2의 MetalLB speaker 재시작.

```
Warning  Unhealthy  pod/speaker-sjvkk  Liveness probe failed: Get "http://127.0.0.1:17472/healthz": context deadline exceeded
Warning  Unhealthy  pod/controller-…   Readiness probe failed: … context deadline exceeded
Normal   Killing    pod/speaker-sjvkk  Container speaker failed liveness probe, will be restarted
Last State: Terminated, Reason: Error, Exit Code: 137
```

노드 CPU가 모자라 speaker가 상태 검사에 제때 응답하지 못했고, kubelet이 재시작시켰다(137 = 강제 종료). 앱만이 아니라 외부 IP를 알리는 구성 요소도 영향을 받는다. → 시스템 구성 요소의 리소스 요청값·우선순위(B2/M6에서 다룸).

## 남은 조사

- **요청 1건당 커넥션 2회 획득**: 대부분의 API는 트랜잭션이 하나다. 1회로 줄면 같은 풀로 처리량이 두 배가 될 수 있다
- 배포가 dev 프로필로 돈다(`show-sql`, `ddl-auto: update` 포함) → 배포용 프로필 분리(B2)
- 측정마다 계약 데이터가 쌓여 조건이 조금씩 달라진다 → 비교 측정 전 데이터 정리
