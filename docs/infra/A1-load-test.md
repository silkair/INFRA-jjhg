# A1 — 실제 API 트래픽으로 한계 측정

M2·M4의 확인은 health·내 정보·업로드 몇 건과 curl 반복뿐이었다. 실제 API 시나리오로 부하를 주고, 어디까지 버티는지와 무엇이 먼저 막히는지 측정했다. 병목을 하나씩 걷어 내며 같은 측정을 반복했다.

## 요약

| 단계 | 조건 | 처리 한계 (요청/초) | 약 120요청/초에서 응답 중앙값 |
|---|---|---|---|
| 기준선 | 워커 2 vCPU, 파드 1개, SQL 출력 켜짐 | 약 100 | 포화 |
| R2 | SQL 출력 끔, 앱·MySQL 같은 노드 | 약 140~155 | 27ms |
| R3′ | 위 + 파드 2개 | 약 130~150 (늘지 않음) | 45ms |
| R5 | 워커 **4 vCPU**, 파드 2개 | 400에서도 정체 없음 | 12ms |
| R5b·R4·R6 | 4 vCPU, 파드 2개 / 1개 / Envoy 우회 | **약 600~700** | 7~12ms |
| R7 | R5b + 요청당 커넥션 획득 2→1회 (코드 수정) | 약 615~650 (변화 없음) | 12ms |

- 직접 병목은 처음부터 끝까지 **DB 커넥션 풀 대기**였다. 커넥션을 쥔 시간의 대부분은 쿼리가 아니라 **노드 CPU 차례를 기다리는 시간**이었다. 워커 vCPU를 2→4로 늘리자 커넥션 점유 시간이 35ms → 2~4ms로 줄고 처리 한계가 약 4배가 됐다.
- 2 vCPU에서도 4 vCPU에서도 **앱 파드를 1개 → 2개로 늘려 처리량이 오르지 않았다.** 이 환경에서는 수평 확장이 답이 아니었다.
- 요청당 커넥션 획득을 2회 → 1회로 줄였지만(9절) 천장은 그대로였다. 커넥션 수요는 천장의 원인이 아니다
- 4 vCPU의 천장(약 600~700)의 원인은 확정하지 못했다(6절).

## 방법

| 항목 | 값 |
|---|---|
| 도구 | k6. 노트북에서 실행하며 VM 3대와 같은 기기를 쓴다(측정 조건으로 명시). 노트북은 16코어(하이퍼스레딩 없음) |
| 가상 사용자 | DB에 100명 시드(`scripts/seed-load-users.sh`). 토큰은 k6가 앱과 같은 규칙(HS512, subject = user id)으로 만든다 |
| 시나리오 1회 | 내 정보 → 계약 목록 → (5회 중 1회) 계약 생성 + 상세 → 안 읽은 알림 수 ≈ 요청 3.4건 |
| 프로필 | ramp: 2분마다 5→10→20→40→PEAK회/초. PEAK는 60(2 vCPU), 120(R5), 250(R5b 이후) |
| 클러스터 | control plane 1대(2 vCPU), worker 2대(2 vCPU → R5부터 4 vCPU, 6GB), MySQL 1개, 앱 커넥션 풀 기본값 10/파드 |
| 지표 | Prometheus 30초 수집. 대시보드 "진짜할게 API" → 성능 진단 행(커넥션 풀, 노드·파드 CPU, 요청당 커넥션 획득 횟수) |

**측정 규칙** (7절의 실수 뒤에 정함)
- 비교는 ramp로 한다. 처음 2분의 저부하가 JVM을 데운다
- 측정마다 새 가상 사용자 접두어(`r1`, `r2` …)를 쓴다
- 비교할 측정은 같은 시간대에 연달아 한다. 시작 전 노트북 메모리 %, 포화 구간의 노트북 CPU %를 적는다
- 측정마다 k6 HTML 보고서와 대시보드 캡처를 남긴다
- 한 번씩만 잰 측정이므로 ±10% 차이는 같은 것으로 본다

| 구간 | 시나리오 (회/초) | 요청 (건/초) | p95 | 실패 |
|---|---|---|---|---|
| 0~6분 | 2 → 19 | 7 → 65 | 30~55ms | 0 |
| 6분~6분 50초 | 19 → 26 | 65 → 87 | 50~140ms | 0 |
| 6분 50초~7분 | 27~28 | 91~95 | 230~260ms | 0 |

- 처리 한계는 **초당 약 100요청**이었다. 그 이상은 처리량이 늘지 않고 대기만 쌓였다
- p95 100ms 이하를 지킨 구간은 초당 약 85요청까지
- 35,789건 중 실패 0건. 처리하지 못한 시나리오 3,124회(k6 가상 사용자 400명 소진)

## 2. 병목 진단 (steady 30회/초, 4분, 조건 하나씩 변경)

| | 0. 처음 | 1. SQL 출력 끔 | 2. 앱을 다른 노드로 |
|---|---|---|---|
| 배치 | 앱·MySQL 모두 w1 | 모두 w1 | 앱 w2 / MySQL w1 |
| 처리량 (요청/초) | 92.7 | **97.9** | 83.1 |
| 응답 시간 중앙값 | 737ms | **314ms** | 1,030ms |
| p95 | 2.0초 | **1.65초** | 2.49초 |
| 처리 못 한 시나리오 | 598 | 278 | 1,271 |
| 커넥션 사용 중 / 대기 (2~3분 시점) | 10/10 · 84 | 10/10 · 8 | 10/10 · 79 |
| 커넥션 대기 시간 (평균) | 0.44초 | 0.24초 | 0.44초 |
| 커넥션 점유 시간 (평균) | 51ms | **35ms** | 51ms |
| 앱 CPU / MySQL CPU (코어) | 0.62 / 0.44 | 0.96 / 0.57 | 1.12~1.35 / 0.70 |
| 노드 CPU | w1 99% | w1 94% | w1 77%, w2 수집 지연(포화 추정) |
| 요청 1건당 커넥션 획득 | — | 2.0회 | 2.0회 |

**0 → 1. 직접 병목은 DB 커넥션 풀 고갈이었다.** 모든 API의 p95가 약 2초로 같았다. 특정 쿼리가 아니라 커넥션 대기라는 공통 지점에서 막혔다는 뜻이다. 원인 하나는 개발용 SQL 출력(`show-sql`, `format_sql`)이 배포 환경(dev 프로필)에 켜져 있던 것이다. SQL을 쿼리 실행 중에 표준 출력으로 찍어서 커넥션 점유 시간이 늘었다. 끄자 점유 시간이 31%, 응답 중앙값이 57% 줄었다.

**배치 원인.** 앱 CPU 요청값은 200m(실사용 0.6~1코어), MySQL은 100m(실사용 0.4~0.7코어)였다. 스케줄러는 요청값으로 배치를 정하므로 둘을 같은 2코어 노드에 두었다. 요청값을 500m씩으로 현실화했다.

**1 → 2. 노드를 나누자 오히려 나빠졌다(예측 실패).** 앱→DB가 노드 간 네트워크를 거치게 되어 점유 시간이 다시 51ms가 됐다. 옮겨 간 w2에는 Prometheus·Envoy·Redis·RustFS가 있어 포화됐다.

**처리량 모델.** 커넥션 풀이 막는 동안의 처리량은 다음 식으로 맞았다.

> 처리량 ≈ 커넥션 수 ÷ (요청당 커넥션 획득 횟수 2.0 × 커넥션 점유 시간)

R1의 예측은 111, 실측은 110~125였다. R2의 예측은 143, 실측은 145~158이었다. 처리량을 올리려면 커넥션을 늘리거나, 점유 시간을 줄이거나, 요청당 획득 횟수를 줄여야 한다.

## 3. 배치와 파드 수 비교 (2 vCPU, ramp PEAK=60)

| | R1 | R2 | R2′ | R3′ |
|---|---|---|---|---|
| 조건 | 파드 1개, 앱·MySQL 다른 노드 | 파드 1개, 같은 노드 | R2 재측정 | **파드 2개** (노드 분산) |
| 처리 한계 (요청/초) | 110~125 | 140~158 | 131~152 | 131~152 |
| 약 120요청/초에서 중앙값 | 315ms (이미 포화) | 27ms | 28ms | 45ms |
| 실패 | 0 | 0 | 0 | 2건 (포화 구간) |

- 앱과 MySQL을 **같은 노드**에 두는 편이 약 25% 높았다. 노드 간 왕복이 커넥션 점유 시간에 더해지기 때문이다
- **파드를 2개로 늘려도 처리량이 늘지 않았다.** 이때 워커 2대의 CPU가 모두 95~100%였다. 커넥션은 20개로 늘었지만 CPU가 모자라 점유 시간이 함께 늘었다. 병목이 커넥션 풀에서 클러스터 CPU로 옮겨 갔다
- R2′·R3′는 같은 시간대에 연달아 쟀다. 처음 잰 R3는 비교에서 뺐다(7절)
- 근거: [R1](evidence/R1-ramp.html) · [R2](evidence/R2-ramp.html) · [R2′](evidence/R2b-ramp.html) · [R3′](evidence/R3b-ramp.html)

## 4. 수직 확장: 워커 vCPU 2 → 4 (R5, 파드 2개, PEAK=120)

| 요청 (건/초) | 응답 중앙값 | p95 |
|---|---|---|
| 98 | 12ms | 21ms |
| 215 | 13ms | 27ms |
| 307 | 15ms | 35ms |
| **397 (최고 단계)** | **19ms** | **45ms** |

- 최고 단계까지 정체가 없었다. 실패 0, 처리 못 한 시나리오 0
- 커넥션 점유 시간이 35~50ms → **2~4ms**, 커넥션 대기 0, 노드 CPU 약 40%였다
- 해석: 쿼리 자체는 원래 빨랐다. 2코어 노드에서 앱·MySQL·Envoy가 CPU를 다투는 동안 **커넥션을 쥔 채 실행 차례를 기다린 시간**이 점유 시간의 대부분이었다
- 함께 바뀐 조건: vCPU를 바꾸려고 노드를 drain해서 파드 위치가 바뀌었다. 앱 이미지가 ShedLock 버전으로 바뀌었다(5분·하루 주기 작업에만 관여)
- 근거: [R5](evidence/R5-ramp.html)

## 5. 천장 찾기 (4 vCPU, PEAK=250, 같은 날 연속 측정)

| | R5b | R4 | R6 |
|---|---|---|---|
| 조건 | 파드 2개 (w1·w2) | 파드 1개 (MySQL과 같은 w1) | R4 + **Envoy 우회** (워커 NodePort로 직접) |
| 처리 한계 (요청/초) | 565~633 | 594~684 | 567~699 |
| p95 100ms 이하 유지 | 약 575까지 | 약 630까지 | 약 590까지 |
| 약 120요청/초에서 중앙값 | 12ms | 11ms | **7ms** |
| 약 460요청/초에서 중앙값 / p95 | 17ms / 45ms | 13ms / 22ms | 8ms / 17ms |
| 노드 CPU 최고 | cp1 85%, w1 83%, w2 63% | cp1 72%, w1 72%, w2 30% | cp1 약 85%, w1 약 75% |
| 노트북 CPU (포화 구간) | 약 80% | 약 76% | 50~60% |
| 실패 / 처리 못 한 시나리오 | 0 / 1,143 | 0 / 799 | 0 / 623 |

- **파드 수**: 1개와 2개의 천장이 같다. 앱 파드 수는 병목이 아니다
- **Envoy**: 우회해도 천장은 거의 같다. 대신 요청마다 약 5ms를 더한다(중앙값 11→7ms). 트래픽이 외부 IP를 받은 노드 → w2의 Envoy → w1의 앱으로 노드를 건너다니는 몫으로 본다. Envoy에는 CPU limit이 없다
- **노트북**: R6에서 CPU 50~60%로 여유가 있었는데도 천장은 같았다. 주원인일 가능성은 낮다
- 세 측정 모두 포화 직전에 커넥션 대기가 쌓였다(대기 최대 약 180~380)
- 근거: [R5b](evidence/R5b-ramp.html) · [R4](evidence/R4-ramp.html) · [R6](evidence/R6-direct.html), 대시보드 캡처 `evidence/R5b-dashboard.png` · `R4-dashboard.png` · `R6-dashboard.png`

## 6. 결론과 한계

**확인한 것**
1. 직접 병목은 커넥션 풀 대기였고, 그 크기는 커넥션 점유 시간이 정했다. 점유 시간의 대부분은 CPU 대기였다
2. 수직 확장(워커 vCPU 2→4)으로 처리 한계가 약 100~150 → 약 600~700요청/초가 됐다
3. 수평 확장(파드 1→2)은 2 vCPU에서도 4 vCPU에서도 처리량을 올리지 못했다
4. Envoy 경로는 지연 약 5ms를 더하지만 천장은 아니다

**확정하지 못한 것: 4 vCPU 천장(약 600~700)의 원인**

| 후보 | 판단 근거 |
|---|---|
| MySQL 1개 | 파드 수와 상관없이 천장이 같아 공통 자원으로 의심된다. 그러나 MySQL CPU는 약 0.9~1.25코어로 여유가 있었다. 막혔다면 무엇(디스크 쓰기, 락, 커넥션 처리)인지 모른다 |
| 노드를 건너는 네트워크 경로 | Envoy 우회로 일부만 제거했다. 진입 노드와 Calico 경로는 그대로다 |
| 노트북(k6, VMware 가상 네트워크) | R6에서 CPU 여유가 있었으므로 가능성은 낮지만 배제하지 못했다 |

판정하지 못한 이유는 측정 해상도다. 지표를 30초마다 수집하는데 포화는 30~60초 안에 지나간다. 이 간격으로는 커넥션 점유 시간의 몇 ms 차이를 가를 수 없었다. 계산 창(`rate[1m]`과 `[2m]`)에 따라 결론이 바뀌었다.

**측정 조건의 한계**: 노트북 1대에서 VM과 부하 도구가 CPU를 나눠 쓴다. 측정은 조건마다 한 번씩이다. 이 수치는 이 환경의 값이며 운영 환경 용량을 뜻하지 않는다.

## 7. 측정 방법에서 바로잡은 것

1. **식은 JVM.** 파드 재시작 직후 steady 측정은 JIT 컴파일 전이라 느리게 나왔다. 비교는 처음 2분이 저부하인 ramp로 바꾸고, 측정마다 새 가상 사용자를 쓰게 했다
2. **다른 시간대 비교.** 처음 잰 R3(파드 2개)는 R1·R2보다 12시간 뒤, 노트북 메모리 88%에서 쟀다. 그대로 비교하면 "파드 2개가 더 나쁘다"는 틀린 결론이 나왔다. R2′와 R3′를 연달아 다시 쟀고, 같은 시간대 연속 측정을 규칙으로 정했다
3. **지표 읽기.** Prometheus UI가 시각을 UTC로 표시해 처음에는 데이터가 없다고 오판했다. 30초 수집에 `rate[1m]`을 쓰면 창 안에 샘플이 2개뿐이라 포화 구간에 0 같은 값이 나온다. 포화 중에도 수집 자체는 성공했다(`up` = 1, 수집 시간 최대 약 1초)

## 8. 측정 중 드러난 문제

**CPU 포화가 인프라 구성 요소로 번짐.** 2절 2단계 측정 중 w2의 MetalLB speaker가 재시작됐다.

```
Warning  Unhealthy  pod/speaker-sjvkk  Liveness probe failed: Get "http://127.0.0.1:17472/healthz": context deadline exceeded
Warning  Unhealthy  pod/controller-…   Readiness probe failed: … context deadline exceeded
Normal   Killing    pod/speaker-sjvkk  Container speaker failed liveness probe, will be restarted
Last State: Terminated, Reason: Error, Exit Code: 137
```

노드 CPU가 모자라 speaker가 상태 검사에 제때 응답하지 못했고, kubelet이 재시작시켰다(137 = 강제 종료). 앱만이 아니라 외부 IP를 알리는 구성 요소도 영향을 받는다. → 시스템 구성 요소의 리소스 요청값·우선순위(B2/M6).

**파드 2개로 늘리자 스케줄러 작업이 중복 실행됨.** 5분 주기 작업이 두 파드에서 58ms 차이로 둘 다 돌았다. ShedLock(Redis)으로 한 번만 실행되게 고쳤다(B1-1).

**롤링 업데이트 뒤 파드 2개가 한 노드에 몰림.** preferred anti-affinity는 자원이 모자라면 무시되고, 실행 중인 파드는 다시 배치하지 않는다(IgnoredDuringExecution). 2회 재현했고 파드를 지워 재배치했다.

**drain 뒤 앱 CrashLoopBackOff.** MySQL이 다른 노드로 옮겨 가는 동안 앱이 DB 연결에 실패해 종료(Exit 1)와 재시작을 반복했다. MySQL이 뜬 뒤 스스로 복구됐다. MySQL readiness가 없고, 앱이 DB를 기다리지 않으며, PDB가 없다 → M6·B1-3.

**매니페스트 키 누락으로 ArgoCD 동기화 실패.** `affinity:` 키를 빠뜨린 app.yaml을 커밋해 파싱 오류가 났다. 커밋 전 `kubectl apply --dry-run=server` 검사를 넣었다 → CI YAML 검사(A2).

## 9. 개선: 요청 1건당 커넥션 획득 2회 → 1회 (R7)

**원인.** JWT 필터가 요청마다 회원을 DB에서 조회했다(탈퇴 회원 차단). 필터는 OSIV보다 앞에서 돌기 때문에 이 조회가 커넥션을 따로 하나 썼다. 측정에서 어떤 API를 섞어도 정확히 2.0회가 나온 이유다.

**선택지.**

| | A. 토큰만 믿기 | B. Redis 캐시 (선택) |
|---|---|---|
| 방식 | 필터의 DB 조회 제거 | Redis `auth:active-user:{id}`(10분) 확인, 없을 때만 DB |
| 탈퇴 회원의 남은 토큰 | 만료까지 통과 | 즉시 거부 (탈퇴 커밋 후 키 삭제) |

B를 골랐다. 기존 보안 검사(탈퇴 회원 차단)를 성능 때문에 빼지 않기 위해서다.

**설계에서 신경 쓴 것**
- Redis 오류 시 DB 결과로 판단한다. Redis 장애가 인증 장애로 번지지 않게 한다
- 그 대체가 의미 있으려면 Redis가 빨리 실패해야 한다. 기존 설정은 명령 제한 시간 60초, 끊긴 동안 명령을 쌓아 두기였다. 끊긴 동안 즉시 거부, 제한 시간 2초로 바꿨다(별도 커밋)
- 탈퇴 시 키는 **트랜잭션 커밋 뒤에** 지운다. 커밋 전에 지우면 그사이 다른 요청이 탈퇴 전 DB를 보고 키를 다시 만들 수 있다
- Principal은 회원 엔티티 대신 id만 가진다. 엔티티가 필요한 유스케이스 4곳은 id를 받고, 연결만 필요한 곳은 조회 없이 참조(`getReferenceById`)를 쓴다

**기능 확인 (배포 후)**

| 확인 | 결과 |
|---|---|
| 첫 요청 | 200, 키 생성, TTL 600초 이하 |
| 탈퇴 | 200 |
| 탈퇴 뒤 같은 토큰 (아직 유효) | **404** |
| 탈퇴 뒤 키 | 없음 |

**부하 비교 (R5b와 같은 조건: 4 vCPU, 파드 2개, PEAK=250)**

| | R5b (수정 전) | R7 (수정 후) |
|---|---|---|
| 요청 1건당 커넥션 획득 | 2.0회 | **약 1.0회** |
| 처리 한계 (요청/초) | 565~633 | 585~648 |
| 약 120요청/초에서 중앙값 / p95 | 12ms / 20ms | 12ms / 21ms |
| 약 400요청/초에서 중앙값 / p95 | 16ms / 40ms | 21ms / 51ms |
| 커넥션 대기 최대 | 약 380 | 약 310 |
| 노드 CPU 최고 | cp1 85%, w1 83%, w2 63% | cp1 약 90%, w1 약 85%, w2 약 75% |
| 노트북 CPU (포화 구간) | 약 80% | 78~82% |
| 실패 / 처리 못 한 시나리오 | 0 / 1,143 | 0 / 962 |

- 커넥션 획득은 의도대로 절반이 됐고, 인증된 요청마다 실행되던 DB 조회 1건이 사라졌다
- **처리 한계는 오르지 않았다.** 차이는 측정 오차 범위다. 커넥션 수요를 반으로 줄여도 포화 직전에 커넥션 대기가 다시 쌓였다. 커넥션 풀은 원인이 아니라 증상이고, 그 앞에서 요청이 느려지는 무언가(노드·호스트 CPU 등)가 천장을 정한다고 본다. 6절 후보 중 "MySQL·커넥션 수요"의 가능성이 낮아졌다
- 중간 부하(약 400요청/초)의 지연은 조금 늘었다. Redis 왕복이 더해진 몫인지, 측정 간 오차인지는 한 번의 측정으로 가를 수 없다
