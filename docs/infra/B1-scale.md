# B1 — 수평 확장: 스케줄러 중복 방지, 자동 확장, 계획된 중단 대비

파드를 여러 개로 늘릴 때 생기는 문제를 하나씩 다뤘다. 순서는 ① 파드 2개에서도 스케줄 작업이 한 번만 돌게 하기 ② 부하에 따라 파드 수를 자동으로 바꾸기 ③ 노드를 비우는 동안 서비스가 멈추지 않게 하기다.

A1에서 확인했듯이 이 클러스터에서는 파드를 늘려도 처리량이 늘지 않는다(노드 CPU가 천장). 그래서 B1의 목적은 성능이 아니라 **동작의 안전성과 가용성**이다.

## 요약

| 단계 | 한 일 | 결과 |
|---|---|---|
| B1-1 | ShedLock(Redis 락)으로 스케줄 작업 중복 실행 방지 (앱 코드 변경) | 파드 2개에서 5분 작업이 매번 1회만 실행 |
| B1-2 | metrics-server(kubelet 인증서 정식 발급) + HPA 2~4개 | 초당 300요청에서 23초 만에 확장 시작, 75초 만에 4개 준비. 부하 종료 5분 뒤 2개로 축소 |
| B1-3 | PDB(maxUnavailable 1) + preStop 10초 대기 | 한 노드에 몰린 파드 2개를 비울 때 실패 **2,041건 → 7건 → 0건** |

## B1-1. 스케줄 작업 중복 실행 방지 (ShedLock)

**문제.** 앱에는 스케줄 작업이 2개 있다(5분 주기 인증 만료 처리, 매일 00:01 계약 상태 전환). 파드를 2개로 늘리자 두 파드가 같은 작업을 58ms 차이로 둘 다 실행했다.

**조치.** ShedLock 6.9.2(Redis 저장소)를 붙였다. 작업을 시작하기 전에 Redis에 락(`job-lock:jjhg:{작업 이름}`)을 잡은 파드만 실행한다.

| 작업 | lockAtMostFor | lockAtLeastFor | 이유 |
|---|---|---|---|
| fiveMinuteSchedule | 4분 | 30초 | 실행 중 파드가 죽어도 다음 주기 전에 락이 풀리게 / 시계가 조금 어긋난 다른 파드가 바로 다시 실행하지 않게 |
| daySchedule | 30분 | 1분 | 같은 이유 |

**확인.** 16:00·16:05·16:10에 각각 한 파드만 실행했고, 실행한 파드 이름이 Redis 락 값(`ADDED:시각@파드명:uuid`)과 일치했다.

이 단계는 앱 코드를 고쳤다(의존성 2개, 설정 클래스 1개, 애너테이션 2곳). 원래 앱은 서버 1대를 전제로 만들어져 있었다.

## B1-2. 자동 확장 (metrics-server + HPA)

### metrics-server — kubelet 인증서를 정식으로

metrics-server는 각 노드의 kubelet에 HTTPS로 접속한다. kubeadm 클러스터의 kubelet은 스스로 서명한 인증서를 써서 검증에 실패한다. 흔한 해결은 `--kubelet-insecure-tls`(검증 끄기)지만 쓰지 않았다.

1. 노드 3대의 kubelet 설정에 `serverTLSBootstrap: true` → kubelet이 클러스터 CA에 인증서를 요청(CSR)
2. 클러스터 공용 설정(`kubelet-config` ConfigMap)에도 넣어 다시 join해도 유지
3. 요청자가 우리 노드 3대(`system:node:k8s-*`)인지 확인하고 CSR 승인
4. metrics-server 차트 3.14.0(앱 0.9.0)을 Helm으로 설치. values는 `k8s/infra/metrics-server-values.yaml`

`kubectl top`에 노드 3대가 모두 나왔다 = 세 노드의 인증서 검증을 통과했다.

> 운영 주의: kubelet 인증서는 만료가 다가오면 다시 요청한다. 그때도 승인이 필요하다(자동 승인 도구는 쓰지 않음).

### HPA 설계 (`k8s/hpa.yaml`)

| 설정 | 값 | 이유 |
|---|---|---|
| 파드 수 | 2~4 | 최소 2: 노드 하나가 죽어도 1개가 남게. 최대 4: 워커 2대에 노드당 2개 |
| 기준 | CPU 요청값(500m)의 70% | |
| 늘릴 때 | 기다리지 않음, 15초마다 최대 2개 | |
| 줄일 때 | 5분 안정화, 1분에 1개 | 잠깐 한가해졌다고 줄였다 늘렸다 반복하지 않게 |

**ArgoCD와의 충돌.** Deployment에 `replicas`가 있으면 HPA가 바꾼 값을 ArgoCD selfHeal이 Git 값으로 되돌린다. Deployment에서 `replicas`를 지웠다(ArgoCD 문서 권장). 지울 때 잠깐 1개로 줄 것으로 예상했지만 줄지 않았다(이유는 확인하지 않음).

### 측정: 초당 300요청 8분 → 멈춤

**예측.** 요청당 앱 CPU 3~4.5ms면 파드 2개 기준 사용률 90~135% → 목표 파드 수 = 올림(2 × 90~135 ÷ 70) = 3~4개.

| 시각 (UTC) | 경과 | 일어난 일 |
|---|---|---|
| 08:07:46 | 0초 | 부하 시작 |
| 08:08:09 | 23초 | CPU 105% 감지 → 3개 |
| 08:08:25 | 39초 | CPU 198% → 4개(최대) |
| 08:08:31 / 08:09:01 | 45초 / 75초 | 새 파드 Ready (생성 후 22초 / 36초) |
| 08:15:46 | — | 부하 종료 |
| 08:20:57 / 08:21:58 | — | 4→3 (약 5분 뒤) / 3→2 (1분 뒤) |

- 예측이 맞았다. 4개로 안정된 뒤 CPU는 62~74%(3개였다면 약 88%)
- 23초 = metrics-server 수집 주기 + HPA 판단 주기
- 초반 198%는 새 파드의 JIT 컴파일과, 혼자 부하를 받던 기존 2개 파드 몫

**새 파드가 합류할 때의 비용.**

| 경과 | 중앙값 | p95 |
|---|---|---|
| 0~40초 (2개) | 16~21ms | 37~53ms |
| 40~90초 (새 파드 합류) | 24~39ms | **70~113ms** |
| 100~300초 (4개 안정) | 14~18ms | 32~45ms |

새로 뜬 Java 파드가 트래픽을 받는 약 1분 동안 p95가 2~3배가 됐다. 실패는 0건.

**파드 수와 지연.** 같은 초당 300요청에서 파드 2개(A1 R8)의 p95는 31ms, 4개 안정 구간은 32~35ms였다. 늘려도 지연이 줄지 않았다(A1 결론과 일치).

**설명하지 못한 것.** 300초 시점부터 파드 수·CPU는 그대로인데 지연이 한 단계 올랐다(중앙값 14→30ms, p95 33→64ms). 같은 시점에 커넥션 점유 시간도 약 6→10ms로 올랐다. 측정 중 쌓이는 계약 데이터 영향을 의심하지만 확인하지 않았다.

## B1-3. 계획된 중단 대비 (PDB + preStop)

### 실험 설계

PDB는 drain 같은 **계획된 중단** 때 앱 파드를 한 번에 몇 개까지 내보낼지 정한다. 파드가 노드마다 하나씩이면 노드 하나를 비워도 어차피 1개만 나가므로 PDB가 차이를 만들지 않는다. 차이가 나는 것은 **두 파드가 한 노드에 몰렸을 때**다. 롤링 업데이트 뒤 실제로 3번 이렇게 됐다(preferred anti-affinity는 자원이 모자라면 무시되고, 이미 뜬 파드는 다시 배치하지 않는다).

- 두 파드가 한 노드에 있을 때 그 노드를 비운다
- `--pod-selector=app=jjhg-api`로 앱 파드만 내보낸다(같은 노드의 MySQL 중단과 섞이지 않게)
- 부하는 초당 약 100요청 5분, drain은 약 1분 30초 시점
- 측정 동안 HPA는 2개로 고정(처음 측정에서 HPA가 4개로 늘려 실험이 흐려졌다 — 아래 P0)
- PDB 없음은 `--disable-eviction`으로 재현한다(PDB를 무시하고 바로 삭제)

### 결과

| | 조건 | drain 시간 | 실패 | 서비스 중단 |
|---|---|---|---|---|
| **P0′** | PDB 없음 | 3.5초 | **2,041건 (6.7%)** | **약 25초** |
| **P1** | PDB | 29.3초 | **7건** | 없음 |
| **P2** | PDB + preStop 10초 | 33.4초 | **0건** | 없음 |
| (P0) | PDB 없음, HPA가 4개로 늘려 다른 노드에 2개가 남은 상태 | 5.4초 | 16건 | 없음 |

**P0′ — PDB 없음.** 두 파드가 동시에 삭제됐다. 대체 파드가 Ready가 될 때까지 약 25초 동안 요청이 전부 실패했다(100~110초 구간 실패율 100%).

**P1 — PDB.** 첫 파드만 나가고 두 번째는 "would violate the pod's disruption budget"으로 다섯 번 거부됐다. 대체 파드가 Ready가 된 뒤(21초)에야 두 번째가 나갔다. 항상 1개 이상이 요청을 받았다. drain은 그만큼 길어졌다.

**P1에 남은 7건의 원인 (Envoy 접근 로그).**

```
"response_code":503, "response_flags":"UF",
"upstream_transport_failure_reason":"delayed_connect_error: Connection_refused",
"upstream_host":"10.244.228.75:8080"   ← 막 종료된 파드
```

파드가 종료 신호를 받고 포트를 닫았는데, Envoy는 목적지 목록이 갱신되기 전이라 그 파드로 요청을 보냈다. PDB는 "몇 개를 동시에"만 정하므로 이 틈을 막지 못한다. 파드 하나가 종료될 때마다 3~8건씩 났다(P0 16건 / 2개, P1 7건 / 2개).

**P2 — preStop 10초.** 종료 신호를 보내기 전에 10초 기다리게 했다. 그동안 Envoy가 목적지 목록에서 이 파드를 뺀다.

```yaml
terminationGracePeriodSeconds: 45     # 10초 대기 + Spring 정상 종료(최대 30초)
lifecycle:
  preStop:
    sleep:
      seconds: 10                     # 쿠버네티스 내장 sleep (이미지에 셸 불필요)
# ConfigMap: SERVER_SHUTDOWN=graceful (Spring Boot 3.4+ 기본값이지만 명시)
```

파드가 Terminating으로 바뀐 뒤 정확히 10초 후 종료됐다(04:43:16 → 04:43:26). 실패 0건, Envoy 503도 0건이었다. 새 파드가 합류하는 동안 p95는 약 90ms까지 올랐다가 돌아왔다.

근거: [P0′](evidence/B1-P0b-drain.html) · [P1](evidence/B1-P1-drain.html) · [P2](evidence/B1-P2-drain.html) · [P0](evidence/B1-P0-drain.html), 파드 기록 `evidence/B1-P*-pods.txt`

### 함께 드러난 것

- **앱 지표는 이 실패를 못 봤다.** 2,041건이 실패하는 동안 대시보드의 5xx 비율은 "No data"였다. 503은 Envoy가 냈고 요청이 앱에 닿지 않았기 때문이다. 지금의 SLO·알림(앱 지표 기준)은 이런 장애를 놓친다 → Gateway(Envoy) 지표로 SLO 보강 필요
- **종료 상태가 `Error`로 표시된다.** SIGTERM으로 끝난 Java 프로세스의 종료 코드(143)다. P2에서 실패가 0이었으므로 요청 처리에는 문제가 없다
- **두 파드가 한 노드에 몰리는 배치**는 PDB로 피해를 줄였을 뿐 배치 자체는 그대로다 → topologySpreadConstraints 검토

## 면접 포인트

- insecure-tls 대신 kubelet 인증서를 정식 발급한 이유와 운영 부담(갱신 시 승인)
- HPA 목표 파드 수 계산과 예측 대비 실측, 새 파드 합류 시 p95 2~3배
- HPA와 GitOps의 replicas 충돌
- PDB가 효과 있는 조건(한 노드에 몰렸을 때)과 없는 조건, 실패 2,041 → 7 → 0
- PDB가 못 막는 실패(엔드포인트 갱신 지연)를 Envoy 로그로 찾아 preStop으로 막은 과정
- 앱 지표 기반 SLO가 Gateway 단계 장애를 못 보는 문제

## 남은 과제

- Gateway(Envoy) 지표 수집과 SLO 보강
- topologySpreadConstraints로 파드 분산 강제 여부 검토(노드 2대에서 maxSkew와 HPA 확장의 관계)
- 부하 중 HPA 축소 시 실패 수 측정(preStop 적용 후 같은 종료 경로이므로 0을 예상하지만 미측정)
- 300초 이후 지연 상승의 원인
- 노드가 갑자기 죽는 **계획되지 않은** 중단은 PDB가 막지 못한다 → A3(M6) 워커 노드 다운에서 측정
